# API

## Overview

The contract a device and a caller code against, under `/v1/messaging`.
A device registers itself in the directory, keeps a pool of key
packages, creates conversations, sends and fetches the MLS messages of
each in order, and keeps its recovery record. A storage service asks
whether a person is one of a conversation's people before it serves a
file sent there. A caller for the assistant reads a conversation and
posts to it.

The contract is one OpenAPI 3.1 document, `api/openapi.yaml`, embedded
in the package `api` as `api.Document`. The server's tests hold it to
the routes the server registers, the Go types of every body, the error
codes and their statuses, the device header and the stated limits, and
check every answer the test suite receives against it. The server does
not serve the document; `latere.ai/x/sdk-go/messaging` vendors it and
is its client.

## Design

### Conventions

Bodies are JSON. Bytes are standard base64 with padding. Every route
needs a bearer token. A person is the token's `sub` claim, and every
`person` in a path or a body is that value; with several issuers
configured, their subjects must be one namespace, since the same `sub`
from two issuers is one person. A device sends
`Sermo-Device: <device id>` on every request it makes as a device;
the routes that act for a device require it, the others check it when
present, and Sermo answers `403 not_your_device` when it names no device
of the caller's that stands.

The conversations list pages by the id of the last conversation of a
page, handed back as `after`, and the log by sequence number, handed
back as `after` too; `limit` is 50 when absent or 0, and 200 at most.
A page of conversations as long as its limit names the next one, which
may be empty.

Nothing takes an `Idempotency-Key`. A conversation's id is the
creator's, so a create sent again answers `409 exists`; a commit sent
again after its first send was taken answers `409 epoch_taken`, and the
device reads the log to see that it was its own.

Errors are `{"error": {"code", "message", "details": {"detail"}}}`:
one code, one fixed sentence for a person, and a detail for a
developer. The codes:

| Code | Status | When |
|---|---|---|
| `invalid` | 400 | The body, a parameter or what it holds is not what the route takes, a message among them that is empty, not of the group, or of a later epoch than the group's |
| `unknown_field` | 400 | The body has a member the document does not describe |
| `missing_token` | 401 | No bearer token |
| `invalid_token` | 401 | The token was refused |
| `not_your_device` | 403 | `Sermo-Device` is missing where required, or names no device of the caller's that stands |
| `forbidden` | 403 | The authorizer said no; or the caller is not one of the conversation's people, or its device not a leaf of the group, or the device fetches what was left for another |
| `not_found` | 404 | No such object |
| `exists` | 409 | A conversation id is taken, a record's id is registered with other keys, or its key is revoked |
| `epoch_taken` | 409 | A proposal or commit for an epoch another commit took first |
| `wrong_epoch` | 409 | An application message for an epoch that has ended |
| `refused` | 422 | The group's public state or the conversation's rules refuse the commit or message |
| `too_large` | 413 | The body, a message or a count is over its bound |
| `authorizer_unavailable` | 503 | The authorizer gave no answer; worth retrying |
| `internal` | 500 | Anything else |

Sermo sets no rate limit of its own.

### Routes

| Method and path | Purpose | Action asked |
|---|---|---|
| `GET /service` | The server's external sender, its key and identity, which every conversation's group names | none |
| `GET /people/{person}/devices` | Every record of the person's directory and every revocation, for the caller to verify | `device.list` |
| `PUT /devices/{device}` | Register the caller's device record, vouched for, or the same record vouched for again | `device.register` |
| `POST /revocations` | Keep a revocation one of the caller's records signs; the revoked device's key packages and transfer are deleted and Sermo proposes its removal from every conversation | `device.delete` |
| `PUT /recovery` | Register the recovery record and the wrapped backup key, replacing the earlier ones | `backup.recovery` |
| `GET /recovery` | The caller's recovery record and wrapped backup key | `backup.recovery` |
| `POST /devices/{device}/transfer` | Leave the backup key sealed to a new device of the caller | `device.vouch` |
| `GET /devices/{device}/transfer` | The new device fetches it, once | `device.vouch` |
| `POST /key-packages` | Publish key packages for the calling device: `{key_packages: [..], last_resort}` | `key_package.publish` |
| `GET /key-packages` | How many the calling device has left, and whether it has a last resort | `key_package.publish` |
| `POST /key-packages/claim` | One key package for each device of a person, for a conversation: `{person, conversation}` | `key_package.claim` |
| `POST /conversations` | Create a conversation from its creator's group info of epoch 0: `{id, group_info}` | `conversation.create` |
| `GET /conversations` | The caller's conversations | `conversation.list` |
| `GET /conversations/{id}` | One conversation: id, kind, level, people, owners, epoch, last sequence number, created and updated | `conversation.read` |
| `GET /conversations/{id}/group-info` | The latest group info with the ratchet tree and external public key | `conversation.read` |
| `POST /conversations/{id}/messages` | Send an MLS message: `{message, welcome, group_info}`; a commit needs its group info, and its welcome when it adds a leaf | `conversation.send`, `conversation.commit`, or `conversation.leave` for a proposal that removes the sender's own leaf |
| `GET /conversations/{id}/messages?after=` | The messages after a sequence number, oldest first, waiting up to `wait` seconds for one | `conversation.read` |
| `GET /welcomes` | The welcomes for the calling device, each with its commit's history notice; one of a conversation the authorizer refuses is left out | `conversation.read` for each |
| `DELETE /welcomes/{id}` | Drop a welcome the device has joined with; only the device it was filed for can | none |
| `GET /conversations/{id}/people/{person}` | Whether the person is one of the conversation's people now: `{person, member}` | `conversation.membership` |

A device is removed by a signed revocation rather than by a delete, so
Sermo can neither remove a device on its own nor undo a removal; the
revocation's signer is a record under the same root as the key it
revokes, as sdk-go's directory checks.

A person is a subject, and Sermo knows no handle, name or address of
one. Finding a person by handle and inviting an address that has no
account are the plane's in front of Sermo: an invitation that resolves
to a subject is a person an owner's device then adds like any other.

### A new device of a person

The device approving a new one hands it, over the pairing, each
conversation's id and the epoch the approving device is in. The new
device joins a conversation either by a Welcome another of its person's
devices sends, or on its own from `GET /conversations/{id}/group-info`
with `messaging.Policy.JoinExternal`, which refuses a group info of
another conversation or of an earlier epoch than the one handed over,
and one Latere's member signed. It then sends its external commit like
any other.

### Creating a conversation

The creator's device sends the group info of epoch 0 with its ratchet
tree. Sermo builds the group's `mls.PublicGroup` from it, which checks
the tree and the signature, and accepts it only if the group id is the
conversation id's bytes, the epoch is 0, the one leaf carries the
calling device's credential and key, the state names the subject alone
as its person and owner with the level off, the required capabilities
are the profile's, and the external senders are Sermo's key alone.

### Sending a commit

Sermo parses the message with `mls.PeekMessage`, takes the
conversation's lock, and for a commit processes it with the group's
`mls.PublicGroup` of the current epoch:

1. The epoch must be the group's: an earlier one is `409 epoch_taken`
   with the current epoch in `detail`, and a later one `400 invalid`.
2. The sender leaf must carry the calling device's credential and key.
3. `messaging.Policy.CheckCommit`, with the directory as Sermo holds it
   and the installation's attestation key, must accept it.
4. The authorizer is asked `conversation.commit` with the change as the
   resource's fields of the identity spec: `changes`, `add_people`,
   `remove_people`, `new_owners` and `new_level`.
5. The group info must describe the new epoch exactly
   (`mls.PublicGroup.VerifyGroupInfo` after the merge), with its ratchet
   tree and external public key, so a device that joins from it later
   joins the group every member holds.

Then, in one transaction, the commit is appended with the next sequence
number, the group's public state and group info replace the old, and
the welcome is filed for each device it adds.

A proposal goes through steps 1 to 4 and is kept pending for the epoch.
An application message is appended if its epoch is the group's and the
calling device has a leaf in the group; which leaf sent it is encrypted,
and the devices check it.

### What Sermo cannot check

A public view of a group verifies signatures, the tree and the
proposals, but not what needs the epoch's secrets: a commit's
confirmation tag, the path secrets it encrypts to each member, or the
key a private message was sent under. So every message Sermo accepts is
kept with the subject and the device whose token sent it, and a commit
that honest devices cannot apply is attributable to that device.

### Later

These are designed with the rest and not yet served:

- **Notices.** Each member device but the sender's gets a content-free
  notice of a new message, through an outbox the plane's push reads.
- **The assistant's routes:** `POST /conversations/{id}/assistant/key-package`,
  a key package of the assistant's member for an owner turning it on
  (`conversation.commit`); `GET /conversations/{id}/transcript?after=`,
  the conversation as the assistant's member reads it
  (`conversation.assistant_read`); and `POST /conversations/{id}/answers`,
  an answer posted to the group as the assistant's member,
  `{text, asked_by, ref}` (`conversation.assistant_post`).

## Acceptance criteria

1. The OpenAPI document lists every route above, and a test holds each
   route's request and response to the Go types, both ways.
2. A request with a member the document does not describe is answered
   `400 unknown_field`.
3. A device that names a device of another subject in `Sermo-Device` is
   answered `403 not_your_device`.
4. A commit for an earlier epoch is answered `409 epoch_taken`, and one
   the rules refuse `422 refused`, and neither changes the log.
5. The sdk-go messaging client's tests run against this document.
